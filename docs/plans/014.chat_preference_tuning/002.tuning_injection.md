# Step 002 — Tuning injection into the chain pipeline

## Goal

Inject the per-(user, world) tuning text into chain-stage prompts via two new
placeholders (`PLAN_TUNING` for tool/planning stages, `TONE_TUNING` for the
writer stage), loaded once at generation start.

## Source files

- `backend/app/services/prompts/placeholder_registry.py`
- `backend/app/services/prompts/default_templates.py`
- `backend/app/services/chain_generation_service.py`

## Test files

- `backend/tests/test_tuning_injection.py` (new)

## Interface intent

- **`placeholder_registry.py`** — register two new `PlaceholderInfo` entries:
  `PLAN_TUNING` (description: accumulated user plan/structure preferences,
  injected into tool/planning stages) and `TONE_TUNING` (accumulated user
  tone/writing-style preferences, injected into the writer stage). Pick the same
  `category` used by the existing dynamic per-session placeholders.
  `VALID_PLACEHOLDERS` derives from the registry, so both become valid
  automatically and surface in the admin pipeline-config UI with no route change.
- **`default_templates.py`** — add `{PLAN_TUNING}` to `DEFAULT_TOOL_PROMPT` and
  `DEFAULT_DIRECTOR_PROMPT`; add `{TONE_TUNING}` to `DEFAULT_WRITER_PROMPT`.
  Place each token in a clearly labelled section so it reads sensibly when empty.
- **`chain_generation_service.py`** (this is a service, so it imports the
  step-001 db module directly — `from app.db import tuning_profiles`; no
  sessions/`select` here):
  - Load the `(chat.user_id, chat.world_id)` tuning profile once at the start of
    the generation run (in `_run_chain_generation`, which already has `chat`).
    If no profile row exists, use empty strings for both values.
  - Thread `plan_tuning` / `tone_tuning` down into `_build_placeholder_values`.
  - In `_build_placeholder_values`, map `PLAN_TUNING` → plan_tuning string and
    `TONE_TUNING` → tone_tuning string (empty string when absent). These flow
    through `_resolve_tool_prompt` / `_resolve_writer_prompt` →
    `resolve_prompt_template` unchanged.
- The tool-stage prompt path supplies `PLAN_TUNING`; the writer-stage path
  supplies `TONE_TUNING`. (Supplying both values to both stages is harmless
  since `resolve_prompt_template` only substitutes tokens the template contains;
  keep the mapping by stage for clarity, but it is acceptable to populate both.)

## Definition of done

1. [test] `PLACEHOLDER_REGISTRY` / `VALID_PLACEHOLDERS` contain `PLAN_TUNING`
   and `TONE_TUNING`. (DoD-1)
2. [test] `resolve_prompt_template("...{PLAN_TUNING}...{TONE_TUNING}...",
   PLAN_TUNING="A", TONE_TUNING="B")` substitutes both tokens. (DoD-2)
3. [test] `_build_placeholder_values` returns `PLAN_TUNING` / `TONE_TUNING` keys
   equal to the supplied tuning strings, and empty strings when none supplied.
   (DoD-3)
4. [test] A chain run for a `(user, world)` with a stored profile produces a
   tool-stage prompt containing the profile's `plan_tuning` and a writer-stage
   prompt containing its `tone_tuning` (assert via the prompt the stage builds,
   or via `_build_placeholder_values` output for both stage paths). (DoD-4)
5. [test] When no profile row exists, the run uses empty tuning strings and does
   not error. (DoD-5)
6. [test] `DEFAULT_TOOL_PROMPT` / `DEFAULT_DIRECTOR_PROMPT` contain
   `{PLAN_TUNING}` and `DEFAULT_WRITER_PROMPT` contains `{TONE_TUNING}`
   (string-membership assertion). (DoD-6)

## Skeleton

### Step 002 — frozen interface (2026-06-30)

Threading approach: two plain string params `plan_tuning: str = ""` /
`tone_tuning: str = ""`, defaulted everywhere, threaded run-loop → stage
runners → resolvers → placeholder map. Loaded once in `_run_chain_generation`
via the directly-bindable `_load_tuning` seam; threading frozen. Both values
passed to both stage paths (harmless; resolver only substitutes tokens present
in the template).

Dependency verified — `app/db/tuning_profiles.py`:
`async def get(user_id: int, world_id: int) -> ChatTuningProfile | None`.
`ChatTuningProfile` exposes `.plan_tuning` / `.tone_tuning` (str). Coder reads
`profile.plan_tuning`/`profile.tone_tuning` or `""` when `get` returns `None`.

Load seam (re-freeze — directly bindable across the air gap; DoD-4/DoD-5 bind
here instead of behind a full chain run):
- `_load_tuning(chat) -> tuple[str, str]` (async) — new. Returns
  `(plan_tuning, tone_tuning)` for the chat's `(user_id, world_id)`, or
  `("", "")` when no profile row exists. Body is a loud stub
  (`raise NotImplementedError("_load_tuning not implemented")`) — does NOT read
  the profile, so both DoD-4 (stored profile → returns its values) and DoD-5
  (no profile → empty, no error) are genuinely true-red until the coder
  implements the real `tuning_profiles.get(chat.user_id, chat.world_id)` call.

Registry / templates (data = the contract):
- `backend/app/services/prompts/placeholder_registry.py` — added `PlaceholderInfo`
  entries `PLAN_TUNING` and `TONE_TUNING` (category `"Pipeline"`); both flow into
  derived `VALID_PLACEHOLDERS`. — new
- `backend/app/services/prompts/default_templates.py` — added `{PLAN_TUNING}`
  (labelled "## Player Preferences (Plan)" section) to `DEFAULT_TOOL_PROMPT` and
  `DEFAULT_DIRECTOR_PROMPT`; added `{TONE_TUNING}` ("## Player Preferences (Tone)")
  to `DEFAULT_WRITER_PROMPT`. — new tokens

Signatures (`backend/app/services/chain_generation_service.py`):
- `_build_placeholder_values(context: ChatContext, chat: Any, turn_facts: str, turn_decisions: str, tools_desc: str, decision: str = "", user_instructions: str | None = None, plan_tuning: str = "", tone_tuning: str = "") -> dict[str, str]` — changed (was without `plan_tuning`/`tone_tuning`); returned dict now also carries `"PLAN_TUNING"` / `"TONE_TUNING"` keys.
- `_resolve_tool_prompt(stage, context: ChatContext, chat: Any, turn_facts: str, turn_decisions: str, tools_desc: str, decision: str = "", user_instructions: str | None = None, plan_tuning: str = "", tone_tuning: str = "") -> str` — changed.
- `_resolve_writer_prompt(stage, context: ChatContext, chat: Any, turn_facts: str, turn_decisions: str, decision: str = "", user_instructions: str | None = None, plan_tuning: str = "", tone_tuning: str = "") -> str` — changed.
- `_run_tool_stage(...)` — changed; appended `plan_tuning: str = "", tone_tuning: str = ""` (after `user_instructions`); forwards both to `_resolve_tool_prompt`.
- `_run_writer_stage(...)` — changed; appended `plan_tuning: str = "", tone_tuning: str = ""` (after `user_instructions`); forwards both to `_resolve_writer_prompt`.
- `_run_chain_generation(...)` — signature unchanged; body now calls `plan_tuning, tone_tuning = await _load_tuning(chat)` at run start (replaces the previous inline `= ""` stub) and threads both into the `_run_tool_stage` / `_run_writer_stage` calls.

Caller-compile edits (out of Source-files scope): None — all new params are
keyword-defaulted, so existing callers (`generate_chain_response`,
`regenerate_chain_response`, tests) compile unchanged.

Compile gate: PASS — all three source modules import cleanly;
`PLAN_TUNING`/`TONE_TUNING` present in `VALID_PLACEHOLDERS`; tokens present in
the three default templates.

Behavior intentionally NOT implemented (true-red for coder): the real profile
read inside `_load_tuning` (raises `NotImplementedError`). This keeps both DoD-4
(stored profile → injected) and DoD-5 (no profile → empty, no error) genuinely
red, bound directly to `_load_tuning`. DoD-1/2/3/6 are satisfied by the plumbing
(registry entries, template tokens, `_build_placeholder_values` keys/params),
which is the frozen contract itself.
