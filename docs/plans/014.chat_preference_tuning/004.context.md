# Step 004 context

Retune trigger rule, SSE `tuning_update` event, and prompt-file convention are
in `context.md`. Step-specific anchors:

## Accept paths

- `chat_service.continue_chat(session_id, user_id, variant_index)` ~:556-608:
  deletes the current active assistant, creates a new `ChatMessage` from the
  chosen variant, restores stats/location, clears variants
  (`_save_variants(chat, [])`). This is the explicit accept; hook the
  approved-feedback write + `maybe_retune` after the commit.
- Implicit accept: sending a new message with `variant_index` set auto-commits
  the viewed variant by calling `continue_chat` before generating — hooking
  inside `continue_chat` covers both explicit and implicit accept.

## LLM call shape

Per-stage calls use `client = await get_llm_client_for_model(model_id)` (from
`app.services.llm_chat`), then `client.chat_with_tools(...)` for tool stages.
The retune call is a plain non-tool completion — confirm the non-tool method on
the client in `llm_chat.py` during skeleton/coding (likely a `chat`/completion
helper). Reuse `chat.text_model_id` for the model. Options can mirror
`chat.text_*` sampling params or use defaults.

## SSE emission

The accept/generation flow already streams events through a queue/emitter with
`caller_role` filtering for editor-only events (`phase`, `variants_update`,
etc., per `quick-reference.md`). Emit `tuning_update` the same way so only
editor+/debug callers receive it. The payload carries the post-retune
`plan_tuning` / `tone_tuning` strings (and the `world_id` as a string).

## Prompt file

Follow `backend/app/services/prompts/` one-file-per-prompt convention with the
5-section docstring; re-export via `prompts/__init__.py`. The existing prompt
files (e.g. the planning/writing prompt builders) are the template.

## db reuse

`db/tuning_profiles.get` / `.upsert` and `db/generation_feedback.list` /
`.insert` are all from step 001. Snowflake ids via `snowflake_svc.generate_id()`
in this service layer.
