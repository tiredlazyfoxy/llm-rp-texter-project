# Step 003 — Reject attribution + scoped regenerate

## Goal

Let a regenerate carry a `scope` (`plan` | `text` | null) and optional
`comment`; for `scope="text"` regenerate ONLY the writer stage reusing the
prior plan; and on every regenerate write a `rejected` feedback row capturing
scope, comment, and the discarded content + plan.

## Source files

- `backend/app/models/schemas/chat.py` (extend `RegenerateRequest`)
- `backend/app/routes/chat.py` (pass scope/comment through the regenerate route)
- `backend/app/services/chat_agent_service.py` (thread scope/comment into the dispatch)
- `backend/app/services/chain_generation_service.py` (writer-only regen path + rejected-feedback write)

## Test files

- `backend/tests/test_reject_attribution.py` (new)

## Interface intent

- **`RegenerateRequest`** — add `scope` (`"plan"` | `"text"` | null; null and
  `"plan"` both mean whole-chain regen) and `comment` (str | null). Both
  optional, defaulting to null/None to preserve existing callers. The backend
  stays permissive and accepts any `scope`+`comment` combination. Note (for
  context, not enforced here): per the frontend contract (step 006) a `comment`
  arrives only with `scope="plan"` (or null); `scope="text"` rejects are always
  comment-less and one-click. The backend does not reject other combinations.
- **`routes/chat.py` regenerate route** — accept the new body fields and pass
  them to `chat_agent_service.regenerate_response`.
- **`chat_agent_service.regenerate_response`** — accept `scope` and `comment`,
  forward to `chain_generation_service.regenerate_chain_response` (chain kind).
  Simple/agentic kinds ignore scope (chain-only feature) — keep their existing
  behavior.
- **`chain_generation_service.regenerate_chain_response`** — accept `scope` /
  `comment`. Before discarding the active assistant message:
  - Write one `ChatGenerationFeedback` row with `verdict="rejected"`,
    `scope=scope` (null when not provided), `comment=comment`,
    `content_snapshot` = the discarded assistant content, `plan_snapshot` =
    the discarded message's `generation_plan` JSON (null if absent), for this
    `session_id` + the turn being regenerated. Snowflake id from the service
    layer.
  - Then branch:
    - `scope == "text"` → **writer-only regen**: load the prior plan from the
      discarded message/variant's `generation_plan`, build writer messages from
      summaries + active msgs + `build_writing_plan_message(plan)`, run ONLY the
      writer stage(s) of the pipeline (skip tool stages), then `_finalize_chain`.
      Reuses the stored plan; does not re-run planning.
    - `scope` in (`"plan"`, null) → existing whole-chain regen (re-plan +
      re-write), unchanged except for the feedback write above.
- The writer-only path must still emit the same SSE events the normal regen
  emits (`phase`, `variants_update`, `done`) so the frontend is unaffected. It
  reuses `_run_writer_stage` and `_finalize_chain`.

## Definition of done

1. [test] `RegenerateRequest` accepts and round-trips `scope` and `comment`,
   and still validates with both omitted (defaults null/None). (DoD-1)
2. [test] A regenerate with `scope="text"` runs only the writer stage(s):
   tool/planning stages are NOT re-run, and the writer receives the prior
   plan (assert the planning stage is skipped and the prior `generation_plan`
   is fed to the writer). (DoD-2)
3. [test] A regenerate with `scope="plan"` (and with `scope` omitted) runs the
   full chain (planning re-executed) — existing behavior preserved. (DoD-3)
4. [test] Every regenerate writes exactly one `ChatGenerationFeedback` row with
   `verdict="rejected"`, the given `scope`/`comment`, the discarded
   `content_snapshot`, and the discarded `plan_snapshot`. The row stores
   whatever `scope`/`comment` were sent (no combination is rejected); in
   practice a non-null `comment` co-occurs with `scope="plan"` per the frontend
   contract. (DoD-4)
5. [test] Writer-only regen still appends the discarded generation to variants
   and emits a `variants_update` (the accept/variant flow remains intact).
   (DoD-5)
6. [manual/live] Live chain regen in chain mode with a real model produces
   coherent text from the reused plan (no automated model call). (DoD-6)
