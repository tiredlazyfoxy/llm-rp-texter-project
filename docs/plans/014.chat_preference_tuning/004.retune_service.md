# Step 004 — Retune service + accept trigger

## Goal

On accept of a turn that had ≥1 reject, call an LLM to re-tune the user's
`(user, world)` profile (plan_tuning if there were plan-scoped rejects,
tone_tuning if text-scoped), upsert it, write an `approved` feedback row, and
emit an editor-only `tuning_update` SSE event.

## Source files

- `backend/app/services/prompts/retune_prompt.py` (new prompt file)
- `backend/app/services/prompts/__init__.py` (re-export the new prompt)
- `backend/app/services/retune_service.py` (new service)
- `backend/app/services/chat_service.py` (hook the accept path)

## Test files

- `backend/tests/test_retune_service.py` (new)

## Interface intent

- **`retune_prompt.py`** — one prompt builder following the 5-section docstring
  convention (PURPOSE, USAGE, VARIABLES, DESIGN RATIONALE, CHANGELOG). Builds
  the system/instruction prompt for the retune LLM call. Inputs (in prose):
  current tuning text for the targeted dimension, the turn's rejected feedback
  rows (their scope + comment + discarded content snapshot), and the finally
  accepted content. Output instruction: produce a revised, concise tuning string
  for that dimension that would have reduced the rejection. Re-export from
  `prompts/__init__.py`.
- **`retune_service.py`** — new service. Responsibilities:
  - `maybe_retune(session_id, user_id, world_id, turn_number, accepted_content,
    queue/emitter)` — entry called by the accept hook. Loads the turn's feedback
    rows via `db/generation_feedback`. If there are zero `rejected` rows, return
    immediately (no LLM call). Otherwise:
    - Partition rejects by `scope`: any `plan` reject → retune `plan_tuning`;
      any `text` reject → retune `tone_tuning`; a null-scope reject counts as
      both (whole-chain reject).
    - For each targeted dimension, build the retune prompt and call the LLM via
      the shared client (`get_llm_client_for_model` + a non-tool `chat`-style
      call; reuse the model the chat already uses — `chat.text_model_id`).
    - Upsert the new value(s) into the `(user, world)` profile via
      `db/tuning_profiles.upsert` (create with a fresh snowflake id if absent;
      preserve the untargeted dimension's existing value).
    - Emit the editor-only `tuning_update` SSE event with the post-retune
      `plan_tuning` / `tone_tuning`.
  - Idempotency/cost: only the targeted dimension(s) are sent to the LLM; a
    clean turn never reaches the LLM call.
- **`chat_service.py` accept hook** — `continue_chat(session_id, user_id,
  variant_index)` (~:556-608) is the explicit accept; the implicit accept goes
  through the same `continue_chat` from the `generate_*` paths. After the accept
  commits (new active ChatMessage created, variants cleared), write one
  `ChatGenerationFeedback` row `verdict="approved"` for the turn, then call
  `retune_service.maybe_retune`. The retune runs only when the turn had ≥1
  rejected row, so wiring it unconditionally at the accept point is correct (the
  service self-gates).

## Definition of done

1. [test] `maybe_retune` makes NO LLM call and does not change the profile when
   the turn has zero rejected feedback rows (clean accept). (DoD-1)
2. [test] With only `plan`-scoped reject(s), retune updates `plan_tuning` only
   and leaves `tone_tuning` unchanged; with only `text`-scoped reject(s), it
   updates `tone_tuning` only. (DoD-2)
3. [test] A null-scope (whole-chain) reject causes both dimensions to be
   retuned. (DoD-3)
4. [test] After retune the new value(s) are persisted via
   `db/tuning_profiles.upsert` and re-fetchable for the same `(user, world)`.
   (DoD-4)
5. [test] The accept path writes exactly one `approved` `ChatGenerationFeedback`
   row for the accepted turn. (DoD-5)
6. [test] `maybe_retune` emits a `tuning_update` event carrying the post-retune
   `plan_tuning` / `tone_tuning` (assert via a stub emitter). (DoD-6)
7. [manual/live] With a real LLM, the retuned text is coherent and reflects the
   rejection comments (no automated model call). (DoD-7)
