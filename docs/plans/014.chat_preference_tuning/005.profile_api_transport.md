# Step 005 — Profile API + frontend transport

## Goal

Add the tuning-profile GET/PUT endpoint (+ service), and the frontend transport
layer: DTO mirrors, the new profile api client, and regenerate scope/comment +
`onTuningUpdate` plumbing in the chat api client. No visual components here.

## Source files

- `backend/app/routes/chat.py` (GET + PUT tuning-profile endpoints)
- `backend/app/services/tuning_service.py` (new: get/update profile for current user+world)
- `frontend/src/types/chat.d.ts` (extend `RegenerateRequest`; add `TuningUpdate` payload)
- `frontend/src/api/chat.ts` (scope/comment on regenerate; `onTuningUpdate` handler)
- `frontend/src/types/tuningProfile.d.ts` (new)
- `frontend/src/api/tuningProfile.ts` (new: GET/PUT profile)

## Test files

- `backend/tests/test_tuning_profile_api.py` (new)

## Interface intent

- **`tuning_service.py`** — business logic for the profile API: get the current
  user's profile for a world (returning empty-string defaults when no row), and
  update (replace) `plan_tuning` / `tone_tuning` (assign a snowflake id on first
  create, preserve `created_at` on update). Calls `db/tuning_profiles` only; no
  sessions, no `select`.
- **Routes in `chat.py`** — `GET` returns the current user's tuning profile for
  a given world; `PUT` replaces `plan_tuning` / `tone_tuning`. Both use the
  step-001 Pydantic request/response schemas; ids serialize as strings. The
  endpoints are reachable by the authenticated user for their own profile; no
  cross-user access.
- **`types/chat.d.ts`** — extend the `RegenerateRequest` mirror with optional
  `scope` (`"plan" | "text"`) and `comment` (string); add a `TuningUpdate` event
  payload type (plan_tuning, tone_tuning, world id as string). No `any`.
- **`api/chat.ts`** — `regenerateMessage` and the at-turn variant accept optional
  `scope` + `comment` and include them in the request body. `ChatSSEHandlers`
  gains `onTuningUpdate`, parsed from the new `tuning_update` SSE event inside
  the private `_streamChat`.
- **`types/tuningProfile.d.ts` + `api/tuningProfile.ts`** —
  `getTuningProfile(worldId)` and `updateTuningProfile(worldId, {plan_tuning,
  tone_tuning})`; DTO mirrors the backend schema exactly.

## Definition of done

1. [test] `GET` returns the current user's profile with empty-string defaults
   when no row exists, and the stored values when present. (DoD-1)
2. [test] `PUT` replaces `plan_tuning` / `tone_tuning`, persists, and a
   subsequent `GET` returns the new values; id serializes as a string. (DoD-2)
3. [test] A second `PUT` updates in place (no duplicate profile row for the same
   user+world). (DoD-3)
4. [test] `frontend: cd frontend && npx tsc --noEmit` passes — new DTOs, the
   profile api client, and the extended chat api client type-check with no
   `any`. (DoD-4)
5. [manual/live] The `tuning_update` SSE event is parsed by `_streamChat` and
   delivered to `onTuningUpdate` (verified live; covered structurally by tsc).
   (DoD-5)

## Dependencies

Step 001 (profile model + db + API schemas). The `onTuningUpdate` plumbing is
exercised live by step 004's emitter; the `scope`/`comment` request fields pair
