# Step 006 — Frontend UI: reject affordances + debug preferences panel

## Goal

Add the chain-mode reject affordances — fast "reject" (plan), fast "reject
generation" (text), and "reject with comment" (plan + comment, showing the
rejected generation) — plus the page-state wiring and the debug-gated
preferences panel that views/edits/reverts plan_tuning + tone_tuning and
refreshes on `tuning_update`.

## Source files

- `frontend/src/user/pages/chatPageState.ts` (reject-scope/comment state + actions; profile state; `onTuningUpdate`)
- `frontend/src/user/components/MessageBubble.tsx` (per-message reject affordances)
- `frontend/src/user/components/ChatInput.tsx` (bottom regenerate reject affordances)
- `frontend/src/user/components/ChatSettingsPanel.tsx` (debug-gated preferences panel)

## Test files

- `frontend/src/user/pages/__tests__/chatPageState.tuning.test.ts` (new — only if a frontend test runner exists; see context)

## Interface intent

In chain mode there are exactly **three reject affordances**, and all three
must be present:

1. **Fast "reject"** (the primary/default reject) — one click, no comment.
   Means "the plan is bad". Sends regenerate with `scope="plan"` →
   whole-chain redo (re-plan + re-write).
2. **Fast "reject generation"** — one click, no comment. Means "the plan is
   fine, only the text is bad". Sends regenerate with `scope="text"` →
   writer-only redo (reuse stored plan).
3. **"Reject with comment"** — opens a free-text comment input that MUST
   display the generation being rejected (the just-streamed assistant message
   / latest variant) so the user can reference it while writing. On submit,
   sends regenerate with `scope="plan"` + the comment text → whole-chain redo.

Resolved rule: **a comment only ever pairs with `scope="plan"`.** The two fast
rejects are always one-click and comment-less; only affordance (3) carries a
`comment`.

- **`chatPageState.ts`** — add reactive state on the page-state class (no
  `useState`): the pending reject comment (only meaningful for the comment
  affordance) and whether the comment input is open, plus the loaded tuning
  profile (`plan_tuning` / `tone_tuning`). Free-function actions:
  - a fast-reject action taking the chosen `scope` (`"plan"` or `"text"`) that
    calls `regenerateMessage` (step 005) with that scope and NO comment.
  - a reject-with-comment action that calls `regenerateMessage` with
    `scope="plan"` + the pending comment, then clears/closes the comment input.
  - an `onTuningUpdate` handler wired into the SSE handlers that overwrites the
    in-memory profile with the event payload.
  - load / save / revert actions for the preferences panel using
    `getTuningProfile` / `updateTuningProfile` (step 005). Revert = reload from
    server (discard local edits).
- **`MessageBubble.tsx`** — in chain mode only, the regenerate control
  (currently the single `IconRefresh` handler) is replaced by the three
  affordances above: a fast "reject" button (`scope="plan"`), a fast "reject
  generation" button (`scope="text"`), and a "reject with comment" control that
  toggles a comment input. The comment input MUST render the rejected
  generation's content (the discarded assistant message / latest variant —
  already available client-side; do NOT add a new fetch) alongside the text
  field, then submit with `scope="plan"` + comment. Non-chain modes keep the
  plain single regenerate (no scope choice, no comment). Keep the existing
  `< N/M >` variant switcher and the green `IconCheck` accept untouched.
  `observer` component.
- **`ChatInput.tsx`** — the bottom regenerate affordance mirrors the same
  chain-mode three-affordance set (fast reject / fast reject generation /
  reject with comment showing the rejected content); non-chain modes keep the
  plain regenerate. `observer` component.
- **`ChatSettingsPanel.tsx`** — a preferences section rendered ONLY when the
  editor+/debug toggle is on (same gating precedent as the existing editor-only
  switches), with editable `plan_tuning` / `tone_tuning`, save + revert buttons,
  refreshed live on `tuning_update`.

## Definition of done

1. [manual/live] In chain mode the per-message and bottom controls expose all
   three reject affordances — fast "reject" (`scope="plan"`, one click), fast
   "reject generation" (`scope="text"`, one click), and "reject with comment"
   (opens a comment input, submits `scope="plan"` + comment); non-chain modes
   show a plain regenerate. (DoD-1)
2. [manual/live] The "reject with comment" input displays the rejected
   generation's content (the discarded assistant text / latest variant) next to
   the comment field, with no new fetch. (DoD-2)
3. [manual/live] Fast "reject" sends `scope="plan"` with no comment (whole-chain
   redo); fast "reject generation" sends `scope="text"` with no comment and
   triggers writer-only regen end-to-end; reject-with-comment sends
   `scope="plan"` + the comment. No affordance ever sends a comment with
   `scope="text"`. (DoD-3)
4. [manual/live] The preferences panel is hidden for players and visible only
   with the editor+/debug toggle on; it shows, edits, saves, and reverts
   `plan_tuning` / `tone_tuning`. (DoD-4)
5. [manual/live] A `tuning_update` event refreshes the panel's values live after
   an accept-triggered retune. (DoD-5)
6. [test] `frontend: cd frontend && npx tsc --noEmit` passes — all UI changes,
   page-state additions, and handler wiring type-check with no `any`. (DoD-6)
7. [test] If a frontend test runner is available, the `chatPageState` fast-reject
   action sends scope with no comment, the reject-with-comment action sends
   `scope="plan"` + the comment, and `onTuningUpdate` updates the in-memory
   profile; otherwise recorded as requires-live-run (see context). (DoD-7)
