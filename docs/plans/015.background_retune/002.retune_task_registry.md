# Step 002 — Background task registry + lifecycle

## Goal

Add an in-memory, per-session background-task registry that runs the step-001
retune core as a detached asyncio task, guaranteeing ≤1 running per session with
cancel-and-restart semantics.

## Source files

backend/app/services/retune_tasks.py

## Test files

backend/tests/services/test_retune_tasks.py

## Interface intent

New module `backend/app/services/retune_tasks.py` holding a module-level registry
`dict[session_id, RetuneJob]` and a per-session lock map so cancel+create is
atomic under rapid triggers. It exposes:

- **A job record** (`RetuneJob`, a small internal structure — `TypedDict` or a
  plain dataclass; skeleton's call) holding the detached `asyncio.Task`, a
  `running` flag, and a `started_at` timestamp.
- **`start(session_id, user_id, world_id, model_id, turn_number)`** — acquires the
  per-session lock, cancels any in-flight job for that session and awaits its
  teardown (so the old task is truly gone before the new one is registered), then
  `asyncio.create_task(...)` a detached coroutine that calls the step-001 retune
  core using its own DB access (the core's DAL calls each open a fresh standalone
  session — no session is passed in from the request). Registers the new job in the
  registry. `turn_number` may be `None` (manual trigger, step 004) or a real turn
  (auto trigger, step 003); it is passed through to the core for logging/prompt use
  only — the registry does NOT gate on it. Returns nothing (fire-and-forget).
- **The detached runner coroutine** — runs the retune core, and in a `finally`
  clears its own entry from the registry (only if it is still the registered job —
  guard against clobbering a newer job that replaced it) and flips `running` to
  false. Must swallow `asyncio.CancelledError` cleanly (cancellation is normal, not
  an error) and log-and-swallow any other exception so a failed retune never leaks.
- **`stop(session_id)`** — acquires the lock, cancels the in-flight job (if any) and
  removes it from the registry, WITHOUT starting a replacement.
- **`status(session_id)`** — returns a lightweight snapshot: whether a job is
  currently running for the session and its `started_at` (or an idle indicator when
  none). Internal shape (`TypedDict`) — the API response schema is step 004's
  domain; this returns raw booleans/timestamp for the service layer to map.

## Definition of done

1. `[test]` After `start(...)`, `status(session_id)` reports running; after the job
   completes, `status(session_id)` reports idle (running→idle transition). (DoD-1)
2. `[test]` Two `start(...)` calls for the same session never leave two live tasks:
   the second cancels the first and only one job is registered/running. (DoD-2)
3. `[test]` A second `start(...)` restarts with the latest arguments
   (cancel-and-restart, D3) — the new job runs the core with the newly supplied
   signal. (DoD-3)
4. `[test]` `stop(session_id)` cancels the running job and leaves the session idle
   with **no** replacement job scheduled (D3 Stop path). (DoD-4)
5. `[test]` `start(...)` for two DIFFERENT sessions leaves both running
   independently (registry is keyed per session). (DoD-5)
6. `[test]` The detached runner swallows `asyncio.CancelledError` and any core
   exception without propagating out of the task, and clears its registry entry in
   all completion paths (success, cancel, error). (DoD-6)
7. `[test]` `start(...)` returns promptly without awaiting the retune core's
   completion (non-blocking scheduling). (DoD-7)

## Dependencies

001 (calls the step-001 retune core; requires it to be emitter-free and to open its
own DB sessions).
