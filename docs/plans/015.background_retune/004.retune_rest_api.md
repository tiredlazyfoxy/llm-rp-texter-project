# Step 004 — Retune REST API (trigger / stop / status)

## Goal

Expose session-scoped REST endpoints to manually trigger, stop, and poll the status
of a background retune for a chat, backed by the step-002 registry.

## Source files

backend/app/routes/chat.py
backend/app/services/tuning_service.py
backend/app/models/schemas/chat.py

## Test files

backend/tests/routes/test_retune_api.py

## Interface intent

- **Service functions** (in `tuning_service.py` — it already owns profile read/write
  and is the natural home; may delegate to `retune_tasks` and `tuning_profiles_db`):
  - **`trigger_retune(chat_id, user_id)`** — manual trigger. Loads the chat, resolves
    its `session_id` / `world_id` / `model_id`, verifies ownership, then calls
    `retune_tasks.start(...)` with `turn_number=None` (session-wide, ignores the D2
    turn-gate — the manual button always fires; zero session rejects makes the core a
    fast no-op). Cancel-and-restart is handled inside `start`.
  - **`stop_retune(chat_id, user_id)`** — verifies ownership, calls
    `retune_tasks.stop(session_id)` (cancel without restart).
  - **`get_retune_status(chat_id, user_id)`** — verifies ownership, reads
    `retune_tasks.status(session_id)` for the `running` flag and loads the current
    `(user_id, world_id)` profile via `tuning_profiles_db.get(...)`, returning a
    combined view: `running`, `plan_tuning`, `tone_tuning`, `world_id`. This lets a
    single poll learn both "finished" (running flipped false) and the new values.
- **Pydantic response schema** in `models/schemas/chat.py` — a `RetuneStatusResponse`
  (`BaseModel`) with `running: bool`, `plan_tuning: str`, `tone_tuning: str`,
  `world_id` (serialized as string). This is the response body for the status
  endpoint. The trigger/stop endpoints may return the same status shape or a minimal
  ack — skeleton's call, but keep it typed (no free dict).
- **Routes** in `routes/chat.py` (HTTP only — parse, call service, return),
  session-scoped under the existing chat prefix:
  - `POST /{chat_id}/retune` → `trigger_retune`
  - `POST /{chat_id}/retune/stop` → `stop_retune`
  - `GET /{chat_id}/retune/status` → `get_retune_status` → `RetuneStatusResponse`
  Ownership: caller must own the chat; a non-owner gets the standard rejection
  (404/403 per existing chat-route convention).

## Definition of done

1. `[test]` `POST /{chat_id}/retune` starts a background job for the chat's session
   (registry reports running afterward) and returns success. (DoD-1)
2. `[test]` `POST /{chat_id}/retune/stop` cancels the running job; a subsequent
   status poll reports `running=false`. (DoD-2)
3. `[test]` `GET /{chat_id}/retune/status` returns `RetuneStatusResponse` with the
   correct `running` flag and the current profile's `plan_tuning` / `tone_tuning` /
   `world_id` (ids serialized as strings). (DoD-3)
4. `[test]` A caller who does not own the chat is rejected on all three endpoints per
   the existing chat-route ownership convention. (DoD-4)
5. `[test]` The manual trigger ignores the D2 turn-gate — it starts a job even for a
   session/turn context that would not auto-trigger. (DoD-5)
6. `[manual/live]` A live manual trigger against a real chain-mode chat produces an
   updated profile once the background job finishes. (DoD-6)

## Dependencies

002 (`retune_tasks.start/stop/status`), 001 (profile persistence contract).
