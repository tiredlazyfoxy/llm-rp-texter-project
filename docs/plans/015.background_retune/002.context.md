# Step 002 — step-specific context

Feature-wide facts (single-process safety, `get_standalone_session` per-DAL-call
freshness, the step-001 core being emitter-free) are in `context.md` under
"Deployment fact that unblocks the design" and step 001's plan.

Step-local facts:

- This is a **brand-new construct**. Today the codebase has NO background-task
  registry / job manager. The only existing `asyncio.create_task` usage is
  per-request inside SSE generators (e.g.
  `chain_generation_service.py:890-907`: `asyncio.create_task(_run_chain_generation
  (...))` drained via `asyncio.Queue`, cancelled in `finally`). Those tasks die
  with the request; the registry's tasks intentionally OUTLIVE the request.
- Single uvicorn process (no `--workers`) → a module-level `dict` is a safe process
  singleton. No DB persistence for status; on restart the registry is empty (idle),
  which is acceptable.
- The retune core (step 001) does its own DB access via the DAL layer, each call
  opening a fresh standalone session — so the detached task must NOT receive or
  hold a request-scoped `AsyncSession`. Pass only ids + `model_id` + `turn_number`.
- Per-session `asyncio.Lock` is required so a rapid auto-accept + manual-trigger
  race cannot interleave cancel/create and leave two tasks. Consider a
  `dict[session_id, asyncio.Lock]` created lazily.
- Tests should drive the registry with a fake/stub core (e.g. an injected or
  patched coroutine that blocks on an event) to observe cancel-and-restart and
  running→idle transitions deterministically without real LLM calls.
