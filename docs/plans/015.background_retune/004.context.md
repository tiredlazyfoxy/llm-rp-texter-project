# Step 004 — step-specific context

Feature-wide anchors (chat routes, tuning_service role, registry API) are in
`context.md`. D3 (cancel-and-restart vs stop) and D2 (manual ignores the turn-gate)
are in "Locked design decisions".

Step-local facts:

- `routes/chat.py` already hosts chat SSE endpoints (`POST /{chat_id}/message`
  :131, `POST /{chat_id}/regenerate` :145) and tuning-profile REST
  (`GET /tuning-profile/{world_id}` :243, `PUT /tuning-profile/{world_id}` :251 →
  `tuning_service.get_profile`/`update_profile`). The new retune endpoints are
  **session/chat-scoped** (`/{chat_id}/...`) because the registry is keyed by the
  chat's session id — do NOT key them by world.
- `tuning_service.py` already exposes `get_profile` / `update_profile` and is
  separate from `retune_service`; put the trigger/stop/status service functions
  here so all profile+tuning HTTP-facing logic stays in one service.
- Chat → session/world/model resolution: the chat record carries `session_id` and
  `world_id`; `model_id` comes from the same place `_record_accept_and_retune`
  obtains it (see the chain/simple auto-commit call sites). The skeleton agent can
  read the chat model to find the exact accessors; do not invent field names.
- Ownership check idiom: follow whatever `GET /tuning-profile/{world_id}` and the
  existing `/{chat_id}/...` chat routes already do (they load the chat for the
  authenticated user and 404/403 on mismatch). Reuse that, don't invent a new one.
- Status returns the profile too so the frontend's single poll (step 005) detects
  the running→idle edge AND gets the new values in one round-trip.
