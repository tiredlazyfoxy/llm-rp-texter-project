# Step 005 — Frontend transport + polling

## Goal

Add the retune REST client + a chat-scoped status-polling loop in page state that
detects the running→idle edge, refreshes the tuning profile, and raises a blink
flag — and remove the old `tuning_update` SSE handler.

## Test files

## Interface intent

- **`api/retune.ts`** (new) — `triggerRetune(chatId, signal?)`,
  `stopRetune(chatId, signal?)`, `getRetuneStatus(chatId, signal?) ->
  Promise<RetuneStatus>`, each via the shared `request<T>` from `./client` hitting
  the step-004 routes (`POST /{chatId}/retune`, `POST /{chatId}/retune/stop`,
  `GET /{chatId}/retune/status`). (Placing these in a new `api/retune.ts` keeps
  `tuningProfile.ts` focused on profile CRUD; `tuningProfile.ts` is listed only if
  a re-export or shared helper is needed — prefer the new file.)
- **`types/retune.d.ts`** (new) — `RetuneStatus { running: boolean; plan_tuning:
  string; tone_tuning: string; world_id: string }`, mirroring the step-004
  `RetuneStatusResponse` exactly.
- **`types/chat.d.ts`** — remove the `TuningUpdate` interface (:155-159); it is
  dead once the SSE event is gone.
- **`api/chat.ts`** — remove `onTuningUpdate?` from `ChatSSEHandlers` (:16) and the
  `case "tuning_update"` branch (:298-301) from `_streamChat`.
- **`chatPageState.ts`** — on `ChatPageState`:
  - Add observables `retuneRunning: boolean` and `retuneJustFinished: boolean`
    (blink flag), both defaulting false; and a non-observable polling handle (a
    timer id / AbortController) alongside the existing `streamCtrl`.
  - Add a polling action pair: `startRetunePolling(state)` — begins a periodic
    `getRetuneStatus(chatId)` loop (interval-based, like the admin page's
    `setInterval`); `stopRetunePolling(state)` — clears it. Start on chat open, stop
    on dispose. On each poll, set `retuneRunning` from the payload; on a
    running→idle EDGE (was true, now false) set `retuneJustFinished = true` and
    refresh `state.tuningProfile` from the status payload's `plan_tuning` /
    `tone_tuning` / `world_id`.
  - Add actions `triggerRetuneNow(state)` (calls `triggerRetune(chatId)` then
    optimistically sets `retuneRunning = true` and ensures polling is active) and
    `stopRetune(state)` (calls the `stopRetune` API then sets `retuneRunning =
    false`). Note the naming collision with the existing generation
    `stopGeneration` — keep them distinct; the retune stop is a new separate action.
  - Add a `clearRetuneBlink(state)` action that resets `retuneJustFinished = false`
    (consumed by step 006 when the panel opens).
  - Remove `applyTuningUpdate` (:699) and every `onTuningUpdate:` wiring in the
    stream handler objects (:349, :421, :504, :612). Keep `loadTuningProfile` /
    `saveTuningProfile` / `revertTuningProfile`.

## Definition of done

1. `[test]` `cd frontend && npx tsc --noEmit` passes with the new `api/retune.ts`,
   `types/retune.d.ts`, the removed `TuningUpdate`/`onTuningUpdate`/`tuning_update`
   references, and the new page-state observables/actions. (DoD-1)
2. `[test]` `cd frontend && npm run build` succeeds (typecheck + bundle). (DoD-2)
3. `[manual/live]` While a retune runs, polling flips `retuneRunning` true; when it
   finishes, the running→idle edge sets `retuneJustFinished` and refreshes
   `tuningProfile` to the new values in one poll. (DoD-3)
4. `[manual/live]` `triggerRetuneNow` starts a job and polling reflects it; `stopRetune`
   halts it; polling starts on chat open and stops on dispose (no leaked interval).
   (DoD-4)
5. `[manual/live]` No `tuning_update` SSE branch remains; live streams still work
   with the handler removed. (DoD-5)
