# Step 001 — Step-specific context

## Where the existing update-settings flow lives

The orchestrator's briefing intentionally does not pin the exact
service / db function names because the planner did not read source
files. The coder will discover them by following
`UpdateChatSettingsRequest` usage from `backend/app/models/schemas/chat.py`
outward:

1. Grep for `UpdateChatSettingsRequest` in `backend/app/routes/`
   to find the `PATCH` settings handler.
2. Follow the handler's call into `backend/app/services/chat_service.py`
   to find the update-settings service function.
3. Follow that into `backend/app/db/chats.py` (or whichever `db/`
   module the service imports from) to find the db-layer helper.

The new `character_name` parameter is added at each of those three
levels in the same style the existing `tool_model` / `text_model`
parameters use (kw-only or positional, default-`None`, etc.).

## Pydantic validator style

The codebase uses Pydantic v2 (project is on Python 3.13). Use
`@field_validator("character_name")` with `@classmethod` and the
`(cls, v)` signature. Raise `ValueError` (not `HTTPException`) on
rejection — FastAPI converts the resulting `ValidationError` to a
422 by default, but project convention for body validation is to
let FastAPI's default mapping do its job. If existing schemas in
`backend/app/models/schemas/` already standardize on a specific
error-response shape, mirror it. (Briefing says "HTTP 400" — that
is what the orchestrator-confirmed contract calls for; coder
confirms the actual default is acceptable, and only adds a custom
exception if existing conventions in the file demand it.)

## Trim-and-reject semantics (single source of truth)

```
input -> v.strip(); if result == "": raise ValueError(...)
return result  # the trimmed value
```

This same logic applies on both create and update. Factor it into
a small private helper at module scope (e.g.
`_normalize_character_name`) if both validators end up identical;
otherwise inline it in each.
