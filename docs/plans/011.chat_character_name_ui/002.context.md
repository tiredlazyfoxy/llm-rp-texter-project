# Step 002 — Step-specific context

## The heuristic being replaced

Today, `frontend/src/user/state/characterSetupPageState.ts`
`submitCharacter` (around lines 121-154) builds the create-chat
payload with:

```ts
character_name: state.variables["NAME"]
  || state.variables[placeholders[0]]
  || "Hero"
```

This is the **only** call site that derives `character_name`. The
template-variables loop (around line 120) that populates
`state.variables` for each declared world template variable is
**not** affected — those inputs and their submission as a separate
template-variables payload (or whatever the field is called on
`CreateChatRequest`) stay exactly as they are.

## Two distinct concepts (do not unify)

- `character_name` — chat-session field; sole source of truth for
  the `{CHARACTER_NAME}` runtime placeholder.
- `state.variables["NAME"]` — a template variable that exists only
  if the world author declared a `{NAME}` slot. Lives in the
  template-variables map, not on the chat session.

These render as two separate inputs on the form. Removing or
hiding the `{NAME}` template input is **out of scope** for this
feature even when the world declares one — the user may want both.

## Settings panel — current shape

Per the briefing,
`frontend/src/user/components/chats/ChatSettingsPanel.tsx` today
edits `tool_model` and `text_model` via `UpdateChatSettingsRequest`.
Coder follows the file's prevailing pattern for:

- Where the editable in-flight values live (local `useState` vs a
  panel-scoped MobX state object).
- How the save button reads "is dirty?" (compare to the loaded
  values).
- How the API call is dispatched (a hook, a state method, a
  service call).

The new "Character Name" row mirrors that pattern; do not
introduce a new state-management approach for this single field.

## Backend contract reminder

After step 001:

- `PATCH /api/chats/{id}/settings` (or whatever the exact path is)
  accepts an optional `character_name` and rejects empty /
  whitespace-only with HTTP 400.
- `POST /api/chats` rejects empty / whitespace-only `character_name`
  with HTTP 400.

Disabling the submit / save button when the trimmed value is empty
keeps users from hitting the 400 in the normal flow.

## Out of scope for this step

- No backend changes (step 001 owns them).
- No removal of the `{NAME}` template-variable input.
- No banner / toast when the name changes mid-chat — the runtime
  picks up the new value silently on the next turn (per
  orchestrator-confirmed decision 3).
- No rewrite of stored chat history.
