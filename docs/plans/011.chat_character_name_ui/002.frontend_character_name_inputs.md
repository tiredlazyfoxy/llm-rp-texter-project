# Step 002 — Frontend: explicit `Character Name` inputs (creation + settings)

## Goal

Replace the heuristic-derived `character_name` on the chat-creation
page with an explicit `TextInput`, and add the same field to the
in-chat settings panel — both wired to the backend via the existing
create / update flows. Empty / whitespace-only values disable the
submit/save button to match the backend contract.

## Files to create or modify

- `frontend/src/types/chat.d.ts` (modify) — add
  `character_name?: string` to `UpdateChatSettingsRequest`.
  `CreateChatRequest`, `ChatSessionResponse`, `ChatSessionListItem`
  already declare `character_name` and need no change.
- `frontend/src/user/state/characterSetupPageState.ts` (modify) —
  - Add `characterName: string` observable (default `""`).
  - Add a setter (e.g. `setCharacterName(value: string)`).
  - In `submitCharacter` (lines 121-154), replace the
    `state.variables["NAME"] || state.variables[placeholders[0]] || "Hero"`
    derivation with `this.characterName.trim()`.
  - Block submission when the trimmed value is empty (return early
    or surface a validation error consistent with the file's
    existing pattern).
  - Keep the per-template-placeholder variables collection
    untouched.
- `frontend/src/user/pages/CharacterSetupPage.tsx` (modify) —
  - Render a `<TextInput label="Character Name" required>` at the
    top of the form (above the template-variable inputs), bound
    to `state.characterName` / `state.setCharacterName(...)`.
  - Disable the submit button when
    `state.characterName.trim() === ""`.
  - Page stays wrapped in `observer`.
- `frontend/src/user/components/chats/ChatSettingsPanel.tsx`
  (modify) —
  - Add a "Character Name" `<TextInput>` row alongside the
    existing `tool_model` / `text_model` selectors. Initialize
    from the loaded chat session's `character_name`.
  - Add local state (or extend the panel's existing state object)
    for the in-flight edited value.
  - On save, send `character_name` through the existing
    `UpdateChatSettingsRequest` API call, alongside any
    `tool_model` / `text_model` change.
  - Disable the save button when the trimmed value is empty.
  - Component stays wrapped in `observer` (if it already is) or
    follows the file's existing reactivity pattern.
- Tests — follow whatever convention the user-side frontend
  already uses. If there are no frontend test files in the
  affected folders, manual verification (described under
  "Definition of done") is acceptable; coder must call this out
  in `status.md`.

## Tests

- If the user SPA already has a component-test or state-test
  setup (e.g. Vitest under `frontend/src/user/**/__tests__/`):
  - State test: `submitCharacter` produces a request body with
    the trimmed `character_name`; refuses to submit when empty.
  - State test: `setCharacterName` updates the observable.
- Manual verification (always required):
  1. Open `CharacterSetupPage`, leave Character Name empty —
     submit is disabled.
  2. Type "  Aria  " — submit is enabled; submitting creates a
     chat with `character_name == "Aria"` (verified via the API
     response or the chat header).
  3. Open the chat's settings panel — the Character Name field
     shows "Aria".
  4. Edit it to "Bran", save — the panel re-renders with "Bran";
     the next chat turn substitutes "Bran" for `{CHARACTER_NAME}`
     in any location/NPC/lore content that uses the token.
  5. Try saving "   " (whitespace only) — save button disabled.

## Definition of done

- `UpdateChatSettingsRequest` in `chat.d.ts` declares
  `character_name?: string`.
- `CharacterSetupPage` shows a labeled "Character Name" input
  above the template-variable inputs; the submit button disables
  when the trimmed value is empty.
- `submitCharacter` no longer references
  `state.variables["NAME"]` or `state.variables[placeholders[0]]`
  to derive the name; it uses the new field exclusively.
- `ChatSettingsPanel` shows a labeled "Character Name" input,
  initialized from the loaded session, sent via the existing
  settings update flow on save; save disables on empty.
- All modified components remain wrapped in `observer` (if they
  were before) or match the file's existing reactivity pattern.
- No `any` types introduced; all new state and props are
  explicitly typed.
- Manual verification steps above pass against a backend with
  step 001 deployed.
- The world template's `{NAME}` variable input is **not**
  removed and **not** auto-synced with the new field — the two
  remain independent inputs.

## Dependencies

- Step 001 — the settings-panel half requires the backend to
  accept `character_name` on `UpdateChatSettingsRequest`. The
  creation-form half does not strictly depend on step 001
  (`CreateChatRequest.character_name` already exists), but the
  feature is shipped as one unit.
