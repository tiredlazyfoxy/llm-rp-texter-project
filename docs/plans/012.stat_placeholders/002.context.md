# Step 002 — Narrow context

## Chat-runtime entrypoints (all five must attach stat fields)

1. `backend/app/services/chat_context.py::_build_runtime_ctx` —
   primary builder used by message rendering.
2. `backend/app/services/chat_service.py` — initial-message branch
   added in Feature 010; calls runtime placeholder helper directly.
3. `backend/app/services/chat_agent_service.py` — agent flow's
   `ToolContext` builder.
4. `backend/app/services/simple_generation_service.py` — `ToolContext`
   builder used by simple-generation pipeline.
5. `backend/app/services/chain_generation_service.py` — `ToolContext`
   builder used by chain-generation pipeline.

## Editor-bound paths (must remain stat-less)

- `backend/app/services/admin_tools.py` — confirmed unchanged.
- Document/world-field editor agent flows — their `ToolContext` /
  runtime ctx instances must not get stat data. If a shared builder
  exists, it must accept a flag (or be split) so editor callers
  pass empty.

## Where the data comes from

- `WorldStatDefinition` rows — queried from the chat's
  world. Existing helpers in `db/worlds.py` (or wherever the LLM
  tool path loads them) are the canonical source. Reuse, don't
  duplicate.
- `ChatStat` rows — keyed `(chat_id, stat_name)`. Existing helpers
  in `db/chats.py` (used by the LLM `set_stat` tool path) are the
  canonical source. The owner field is on the row itself or on the
  matching `WorldStatDefinition` — whichever the existing schema
  uses; do not introduce a new owner inference path.

## Layer separation reminder

- Routes never call `db/` directly here (no route changes in this
  step).
- Services may compose `db/` queries.
- `db/` functions own all session creation; do not pass sessions
  into services from this step.

## No step-specific surprises

If during implementation a chat-runtime path is found that wasn't
in the list above, stop and hand back to the orchestrator — the
harvester missed it and the planner needs to update step 002 (or
add a sibling step) before continuing.
