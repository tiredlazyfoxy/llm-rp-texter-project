# Step 004 — Narrow context

## Existing pieces to reuse (do not reimplement)

- `backend/app/services/stat_service.py::validate_and_apply_stat_updates`
  — this is the LLM tool's validation+apply path. The admin
  endpoint must go through it.
- The SSE emitter that publishes `stat_update` to the chat's
  active subscribers — same helper used by the agent's `set_stat`
  tool. The frontend listens on the existing event name; we must
  not introduce a new event name.
- Admin-role dependency — already used by other admin routes in
  `backend/app/routes/`. Follow the existing pattern; do not roll
  a new auth check.

## Layer boundaries (strict)

- `routes/chats.py` — parse request, call service, return
  response. No DB access.
- `services/stat_service.py` — orchestration; calls `db/`
  functions and the SSE emitter.
- `db/chats.py` (or `db/chat_stats.py`) — owns the session and
  the actual `ChatStat` writes. If a multi-stat batch helper does
  not exist, add one — do not write a session inside the service.

## Stat-kind reminder for request validation

- `kind == "int"` → `value: int`
- `kind == "enum"` → `value: str`, must be a member of the
  definition's allowed values
- `kind == "set"` → `value: list[str]`, every element must be a
  member of the definition's allowed values; duplicates rejected
  by the existing validator

These match what the LLM tool already validates, which is why we
reuse `validate_and_apply_stat_updates`.

## No step-specific surprises

If `validate_and_apply_stat_updates` does not exist with that
exact name, find the equivalent in `stat_service.py` and use it.
Do not duplicate the validation logic.
