## Notes & Issues

### Step 001
- **Snapshot shape choice (open trade-off).** The step file used a placeholder type `dict[tuple[str, str], ChatStat]`, but the codebase has no `ChatStat` model — chat stat values live as JSON dicts on `ChatStateSnapshot.character_stats` / `.world_stats`, and `stat_validation.validate_single_value` already pre-types them as `int | str | list[str]`. Picked the precomputed-map shape (`stat_values: dict[tuple[str, str], int | str | list[str]]`) keyed by `(owner, name)` and kept `stat_definitions: list[WorldStatDefinition]` for kind/declared-order lookup. This matches Feature 010's pattern of carrying small typed values directly on the TypedDict. Architect may want to record this on `quick-reference.md` when finalizing.
- **Set iteration order.** Picked `WorldStatDefinition.enum_values` declared order when parseable (falls back to stored iteration order). Documented in the helper docstring.
- **`TypedDict` switched to `total=False`.** All existing callers still populate the three Feature 010 keys, so runtime is unchanged; the relaxation only allows editor-mode dummies / step-002 wiring to add the new optional fields. The helper now uses `.get(..., "")` for the legacy keys so a missing key resolves to empty string instead of `KeyError` — strictly safer.

### Step 002
- **Helper shape choice (open trade-off).** The step file suggested `services/stat_service.py::load_chat_stat_snapshot(chat_id) -> tuple[list[WorldStatDefinition], dict[(owner,name), value]]`, but `chat_context.build_chat_context` and the four generation services already load `stat_defs` + raw stat dicts in scope (the chain-generation tool stage even pre-parses them as locals). A chat-id-only signature would force a re-load at every site. Chose a pure builder `runtime_placeholders.build_stat_values_map(stat_defs, character_stats, world_stats)` instead — same centralization benefit, no DB hit, every call site stays one composition step. Architect may want to record this on `quick-reference.md`.
- **`ChatContext` widened with raw dicts.** Surfaced `character_stats_raw` / `world_stats_raw` on `ChatContext` so `simple_generation_service` and `chain_generation_service` (writer stage) consume one source instead of re-parsing JSON off `ChatSession`. The chain-tool stage and `chat_service.create_chat` already had the raw dicts in local scope, so they pass them directly without going through `ChatContext`.
- **`chat_agent_service.py` does NOT build a runtime ctx or `ToolContext`.** The step file lists it (and the harvested context flagged "locate its `ToolContext` builder"), but inspection shows the file is purely a dispatcher (`generate_response`, `regenerate_response`, `_resolve_pipeline`) that hands work to `simple_generation_service` / `chain_generation_service` — no chat-runtime context construction lives there. Treated as no-op for this step (not the escape valve, since the listed surface is missing rather than extra). Architect may want to drop it from `context.md`'s chat-runtime list.
- **`admin_tools.py` and `summarization_service.py` confirmed unchanged via `git diff` — no stat data leaks into editor/summarization flows.**

### Step 006
- **Refresh strategy choice (per orchestrator delta 1).** Step 004 dropped the SSE-emit, and the response's `applied` list echoes the *requested* (pre-clamp) values rather than the persisted values — so neither the SSE handler nor the response alone can refresh the snapshot faithfully. This reuses the same merge path as `regenerate` / `editMessage` / `deleteMessage` and avoids duplicating snapshot-mutation logic. The existing `applyStatUpdate` SSE handler (used by the LLM tool path during streaming) is left untouched.
- **Trigger gating widened to admin+editor (per orchestrator delta 2).** The step file says admin-only; backend (per step 004 follow-up) gates on `require_role(UserRole.editor)` minimum, so admin still passes but so does editor. Frontend matches: `role === "admin" || role === "editor"`. This keeps UI gating in sync with the actual server gate.
- **No frontend tests (per orchestrator delta 3).** Same precedent as step 005 — `frontend/package.json` has no test runner. ### Step 004 — BLOCKED (escape valve, superseded by resolution above)

- **Step.** `docs/plans/012.stat_placeholders/004.admin_stats_endpoint.md`.
- **What the step asked for (quote, Definition of done).**
  > "SSE `stat_update` event is emitted using the same helper the LLM tool path uses (verified by test)."
  > 004.context.md: "The SSE emitter that publishes `stat_update` to the chat's active subscribers — same helper used by the agent's `set_stat` tool."
- **What conflicts.**
  - There is no `set_stat` tool — the LLM stat-mutation tool is named `update_stat` (see `chat_tools.py::_b_update_stat`, registered in `TOOL_REGISTRY` with that name). The two stat-emit code paths are inline `await queue.put(sse("stat_update", {...}))` in `simple_generation_service.py` (line 317) and `chain_generation_service.py` (line 545). Both write into a *per-request* `asyncio.Queue` owned by the single in-flight LLM streaming generator that is currently producing tokens for that chat. The frontend SSE client receives those events through that same generator's `StreamingResponse`.
  - There is no SSE broker, no chat-scoped subscriber registry, no `sse_events.py` (the `context.md` "or wherever stat_update is emitted" speculation does not match reality), and no helper function wrapping the emit. Crucially, **a chat does not have a persistent SSE channel**: its only SSE stream exists for the lifetime of one generate/regenerate call.
  - An admin `PUT /api/chats/{chat_id}/stats` request is, by design, not part of any LLM streaming generation, so it has no queue to push into and no live subscribers it can fan out to. "Reuse the same helper the LLM tool path uses" is therefore vacuous: extracting the inline emit into a helper does not give the admin route somewhere to publish.
- **Why it blocks.** Satisfying the Definition of done (and the matching test "SSE emitter is invoked once per applied stat") requires architectural surgery the step does not authorize: introducing a chat-scoped pub/sub bus (e.g. `chat_event_bus` keyed by `chat_id`, with the streaming services registering their queue on entry and unregistering on exit, and the admin endpoint publishing into all registered queues for that chat). That is a cross-cutting change to two streaming services + a new module + reload semantics on the frontend (which today only mounts the SSE handler during an in-flight generation). Item 7 in `context.md`'s scope/decisions and the "reused unchanged" wording for `sse_events.py` both signal the planner expected an existing emit helper that does not exist.
- **Suggested resolution(s) with tradeoffs.**
  1. **Drop the SSE-emit requirement (smallest scope).** Admin `PUT /api/chats/{chat_id}/stats` reuses `validate_and_apply_stat_updates` and persists via `db.chats` (new `update_chat_stats` helper); the response itself returns the applied state, and the admin drawer (step 006) refreshes from the response. Rationale: today the frontend only listens for `stat_update` while a generation stream is open — outside that window there are no subscribers anyway, so emitting would be a no-op. Risk: future viewers (e.g. spectator mode) wouldn't see the update; but no such viewer exists today.
  2. **Add a chat-scoped event bus (medium scope).** New module `services/chat_event_bus.py` exposing `subscribe(chat_id) -> Queue`, `unsubscribe(chat_id, queue)`, `publish_stat_update(chat_id, char_stats, world_stats, turn_number)`. Refactor the two inline emits in `simple_generation_service` / `chain_generation_service` to register their queue on stream entry, publish through the bus, and unregister on exit. Admin endpoint publishes through the same helper. Cost: small but real cross-cutting change, plus a frontend story for subscribing outside generation windows if anyone wants the admin edit to fan out to a separately-opened SSE listener (none exists today).
  3. **Re-scope the test contract.** Keep the helper extraction (option 2's bus) but accept that the admin endpoint may publish into "zero subscribers" today — the test verifies the helper is *called* with the expected payload, not that any client receives it. Frontend integration in step 006 covers refresh.
- **Recommendation.** Option 1 is the smallest change consistent with the existing architecture, frontend behavior, and feature 012's other steps. Option 2/3 if the architect explicitly wants a future-proof bus. The user/architect should pick before this step proceeds.
