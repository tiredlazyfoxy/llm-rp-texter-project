# Step 003 — Frontend: wire placeholder UI into WorldFieldEditPage

## Goal

When `WorldFieldEditPage` is editing the `initial_message` field,
render `<PlaceholderTextarea>` plus `<PlaceholderPanel>` (mirror
of `PipelineStageEditPage`) with the three feature-defined
placeholders. The `description` field continues to use a plain
`<Textarea>`.

## Files to create or modify

Create:
- `frontend/src/admin/components/placeholders/initialMessagePlaceholders.ts`
  — a constants file exporting the three placeholders.

Modify:
- `frontend/src/admin/pages/WorldFieldEditPage.tsx` — branch on
  `state.fieldName === "initial_message"`. In that branch render
  the placeholder UI; otherwise keep the current `<Textarea>`.

Read-only (referenced for type info only — do not modify):
- `frontend/src/admin/pages/worldFieldEditPageState.ts` —
  `type WorldFieldName = "description" | "initial_message"`.

## Signatures

```ts
// frontend/src/admin/components/placeholders/initialMessagePlaceholders.ts
import type { PlaceholderInfo } from '../../../types/pipeline';

export const INITIAL_MESSAGE_PLACEHOLDERS: PlaceholderInfo[] = [
  {
    name: 'CHARACTER_NAME',
    description: 'The chat session character name',
    category: 'Character',
  },
  {
    name: 'LOCATION_NAME',
    description: 'The starting location name',
    category: 'Location',
  },
  {
    name: 'LOCATION_SUMMARY',
    description: 'The starting location content / summary',
    category: 'Location',
  },
];
```

`WorldFieldEditPage.tsx` gains (sketch — coder writes the actual
JSX following the project's component rules):

- A `useRef<PlaceholderTextareaController | null>(null)` held in
  the component (this is the documented imperative-API escape
  valve from `frontend-components.md`; not page state).
- A conditional render: when editing `initial_message`, replace
  the existing `<Textarea>` block with `<PlaceholderTextarea>` +
  `<PlaceholderPanel>`. The `onInsert` handler calls
  `controllerRef.current?.insertAtCursor('{' + name + '}')` —
  same wiring `PipelineStageEditPage` already uses.
- The `value` / `onChange` plumbing into page state stays
  identical to today (the textarea is already bound to draft
  state — only the wrapper changes).

No new exported component, no new state class — the two existing
imported components and the pre-existing page state cover the
need.

## Tests

The codebase does not currently have automated UI tests for
`WorldFieldEditPage`. Verification is mechanical + manual smoke:

- `npx tsc --noEmit` clean.
- `npx vite build` succeeds.
- Manual smoke (verifier): open
  `/admin/worlds/<id>/field/initial_message`. Confirm that
  - the placeholder badge panel renders with the three tokens,
  - clicking a badge inserts `{CHARACTER_NAME}` /
    `{LOCATION_NAME}` / `{LOCATION_SUMMARY}` at the cursor,
  - typing `{CHA` triggers the autocomplete dropdown,
  - selecting from the dropdown inserts the full token,
  - the LLM chat panel (`LlmChatPanel`) still works for the
    `initial_message` field as before.
- Manual smoke: open
  `/admin/worlds/<id>/field/description`. Confirm that the
  `description` editor renders as a plain `<Textarea>` (no
  placeholder badges), unchanged from current behavior.

## Definition of done

- `initialMessagePlaceholders.ts` exists with the three
  `PlaceholderInfo` entries (uppercase `name`, no surrounding
  braces — braces are added at insertion time).
- `WorldFieldEditPage.tsx` renders the placeholder UI **only**
  for `initial_message`; `description` is unchanged.
- The component file imports exclusively from
  `components/placeholders/...` (i.e. depends on step 002).
- `controllerRef` insertion mirrors the
  `PipelineStageEditPage` pattern exactly.
- `npx tsc --noEmit` and `npx vite build` both succeed.
- Both manual smoke checks pass.
- The page is wrapped in `observer` (it already is — preserve
  it).
- No `any` types introduced; no React Context introduced.
