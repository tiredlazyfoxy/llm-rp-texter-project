# Step 002 — context

## Why a new folder rather than reusing `pipelines/`

`docs/architecture/frontend-layout.md` Rule 4: page-aware
components live under `components/<domain>/`. The placeholder
components are now consumed by two domains (pipelines, worlds),
so the right home is a domain-neutral admin folder — not
`pipelines/` (a different domain) and not `common/` (these
components are admin-only and depend on `PlaceholderInfo`, a
domain DTO).

`frontend/src/admin/CLAUDE.md` already documents
`components/pipelines/` as containing the placeholder trio plus
`placeholderAutocompleteState.ts` and explicitly mentions the
`PlaceholderTextareaController` shape. That paragraph is what
moves to the new `components/placeholders/` entry.

## Imports inside the moved files

The internal imports between the four moved files (e.g.
`PlaceholderTextarea` importing `placeholderAutocompleteState`,
`PlaceholderTextarea` importing `PlaceholderSuggestions`) are
relative (`./placeholderAutocompleteState`) and continue to work
unchanged after the move. The only imports that need updating
are external consumers' paths.

## `PlaceholderInfo` location

Stays in `frontend/src/types/pipeline.d.ts`. The orchestrator
suggested potentially moving it to a more general types file;
the planner declined to bundle that move into this feature
because:
- It would expand the diff beyond the 50-200-line target.
- The type is still a DTO (`category` is a free string the
  pipeline registry chose), and `pipeline.d.ts` is a fine home
  while the only producer remains the pipeline placeholder
  registry.
A future feature can rename / relocate the type if a non-
pipeline producer appears.
