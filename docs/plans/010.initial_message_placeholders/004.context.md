## Current-location semantics

For chat_context, the placeholders resolve to the **current**
location (the player's present location), not the starting
location. The session's current_location is already loaded by
`build_chat_context` for its other purposes; the same value is
used to populate `RuntimePlaceholderContext.location_name` /
`location_summary`. `character_name` comes from
`session.character_name`.

For `chat_service.py` at chat creation, current == starting (the
chat has just been created), so the existing behavior is
preserved by definition.

## Helper layer placement

The helper lives in `backend/app/services/runtime_placeholders.py`
because `chat_service` and `chat_context` (both in `services/`)
need it. It must be **pure** — no DB, no `session`, no imports
from `app.db.*`. This keeps the layering clean: the `services/`
layer owns business logic, and a pure-function helper is fine
there.

## Distinction from `rewrite_initial_message_tokens`

`backend/app/db/worlds.py` already exposes a
`rewrite_initial_message_tokens()` from step 001 that handles
**source-data lowercase → uppercase normalization** (a one-time
data migration concern). That helper is unrelated to
`apply_runtime_placeholders`, which does **runtime value
substitution**. Do not merge them.
