## World-field-editor prompt — escaping pitfall

`backend/app/services/prompts/world_field_editor_system_prompt.py`
`_FIELD_ROLES["initial_message"]` (lines 43-47) is currently one
line. The whole `_FIELD_ROLES` mapping is consumed by a
`.format(world_name=...)` call at line 146. Therefore any literal
`{CHARACTER_NAME}` written in the role string would be interpreted
as a format placeholder and raise `KeyError`. The new multi-line
block must use **doubled braces** (`{{CHARACTER_NAME}}`,
`{{LOCATION_NAME}}`, `{{LOCATION_SUMMARY}}`) so that after
`.format()` the rendered prompt contains a single pair of braces.

Verification: the test for the world-field-editor prompt asserts
the rendered string contains literal `{CHARACTER_NAME}` (one set
of braces, not two), proving the escaping is correct.

## Placeholder block — wording sketch

The exact wording is the coder's call. The block must convey, at
minimum:
- The three uppercase tokens, each in braces, listed.
- One-line semantics per token (player's character name; current
  location's name; current location's summary/content).
- That the substitution happens at chat time before the player
  sees the rendered text.
- A nudge to use the tokens where they would otherwise hardcode
  the player's name or the current location.

Two prompts, same block (subject to the doubled-brace escaping in
the world-field one). Single source-of-truth wording is encouraged
but not required — keep both readable in their own context.

## Out of scope

`_FIELD_ROLES["description"]` does **not** get the placeholder
block. Description text is not runtime-substituted anywhere in the
backend; teaching the AI to emit placeholders there would produce
broken output.
