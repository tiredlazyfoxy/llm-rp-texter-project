# Step 007 — Context

## DocumentEditPage current shape

`frontend/src/admin/pages/DocumentEditPage.tsx`:
- Line 18 imports `Textarea` from Mantine.
- Lines 214-223 render `<Textarea label="Content" ... />` bound to
  `state.draft.content`. This is the block to replace.
- Line 226 begins the `<LlmChatPanel>` section — leave intact.

The page is already wrapped in `observer`. State lives in
`documentEditPageState.ts`; `state.draft.content` exposes
`value` / `onChange` semantics compatible with the Mantine
`Textarea` it replaces, so `PlaceholderTextarea` slots in without
state-class changes.

## Constants rename rationale

The original module name (`initialMessagePlaceholders.ts`) ties
the constants to a single page. Now that the same trio is reused
by `DocumentEditPage`, the file is renamed `runtimePlaceholders.ts`
and the export becomes `RUNTIME_PLACEHOLDERS` to reflect that
these are the **runtime** placeholders substituted by the chat
runtime — wherever they appear. One source of truth, two import
sites.

`git mv` preserves history; do not delete-and-recreate the file.

## Mirror the existing pattern

`WorldFieldEditPage.tsx` (step 003) is the canonical example for
the wiring:
- `useRef<PlaceholderTextareaController | null>(null)` held in
  the component (imperative-API escape valve documented in
  `docs/architecture/frontend-components.md`).
- `<PlaceholderTextarea>` + `<PlaceholderPanel>` rendered side by
  side; panel's `onInsert` calls
  `controllerRef.current?.insertAtCursor('{' + name + '}')`.

Copy that pattern verbatim into `DocumentEditPage` for the
Content field. No need to invent a new arrangement.

## Out of scope

- The `Name` input on `DocumentEditPage` does **not** get a
  placeholder panel — names are not runtime-substituted.
- No backend changes in this step. Backend substitution for
  document content lives in steps 004 + 005.
- No new placeholder tokens. The set is fixed at three.
