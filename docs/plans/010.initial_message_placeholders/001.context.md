## Migration semantics

- **Idempotent**: re-running the migration on already-uppercase
  rows must return `0` rows changed and not write to the DB.
- **Strict-replace**: only the three known lowercase tokens are
  rewritten. Any other `{...}` content in `initial_message` is
  left alone — users may have legitimate brace text there.
- **Single pass**: implement as a single `UPDATE ... SET
  initial_message = REPLACE(REPLACE(REPLACE(...)))` is acceptable
  if the coder prefers SQL-side; or load → rewrite → save per row
  via the existing world db helpers. Either is fine as long as
  the layer separation rule holds (no SQL in services).

## Why the chat service does not import the rewrite helper

The chat service handles **runtime value substitution** (replace
`{CHARACTER_NAME}` with the actual character name). The migration
helper handles **token-shape rewriting** (lowercase → uppercase).
These are different operations with different lifetimes — coupling
them risks the chat service silently fixing un-migrated rows and
masking migration bugs.
